# سامانهٔ کارما — سند تحویل برای بازنویسی (نسخهٔ ۱)

> **مخاطب:** تیم فنی که بازنویسی سامانه را بر عهده می‌گیرد.
> **مالک محصول:** گروه صنعتی کارما (نام حقوقی: آلیاژ پیچ کار ماد).
> **وضعیت فعلی:** نمونهٔ اولیهٔ کامل (پروتوتایپ HTML) و نسخهٔ عملیاتی روی Google Apps Script + Google Sheets (نسخهٔ 1.3.0).
> **هدف این سند:** آنچه باید ساخته شود، چرا معماری فعلی کنار گذاشته می‌شود، و معیار پذیرش هر بخش.

## ۰. خلاصهٔ تصمیم‌ها

| موضوع | تصمیم |

## ۱. وضعیت فعلی و دلیل بازنویسی

### ۱.۱ آنچه امروز وجود دارد

- **پروتوتایپ** (`Karma-prototype-v2.html`، یک فایل حدود ۲۵ مگابایت). مرجع کارکردی و ظاهری است؛ رفتار همهٔ صفحه‌ها را از روی آن ببینید.
- **نسخهٔ گوگل‌شیت** (`Karma-GoogleSheets-v1.3.0.zip`):
  - `Code.gs`: ورود، نقش‌ها و ذخیره در شیت؛
  - `karma-assets.zip`: اپ، تصاویر و داده‌های اولیه.
- **راهنمای کاربر** (Claude Doc): «راهنمای کاربر سامانهٔ کارما». رفتار فعلی هر نقش را توضیح می‌دهد.
- **دادهٔ محصول در همین مخزن:**

| مسیر | محتوا |
|---|---|
| `output/DIN_full_tables.json` | جدول کامل ابعاد ۳۲۹ استاندارد DIN، استخراج‌شده از فایل‌های منبع |
| `output/DIN_full_tables_audit.json` | گزارش پوشش استخراج |
| `output/DIN_SKU_list.xlsx` | فهرست SKU در سطح سایز (Parents / SKUs / Review) |
| `astm/پیچ و مهره ASTM.xlsx` و `astm/drawings/` | داده و نقشه‌های ASTM |
| `out/Karma-standards-list.xlsx` | فهرست همهٔ استانداردهای کاتالوگ |
| `data/raw/` | فایل‌های منبع DIN |
| `scripts/` | اسکریپت‌های استخراج |
| `docs/content-final.md` | متن نهایی سایت |

- حدود ۱۰۲۰ تصویر محصول و نقشهٔ فنی داخل بستهٔ assets.

### ۱.۲ ایرادهای ساختاری (چرا بازنویسی)

۱. **منطق کسب‌وکار در مرورگر است.**
   - محاسبهٔ مبالغ، شماره‌گذاری، صدور سند حسابداری و کنترل دسترسی همه سمت کلاینت انجام می‌شود.
   - سرور فقط یک JSON بزرگ ذخیره می‌کند و اعتبارسنجی واقعی ندارد.

۲. **دادهٔ یکپارچه به‌جای مدل رابطه‌ای.**
   - هر بخش (فروش، حسابداری، دبیرخانه، …) یک «ریشهٔ» JSON است.
   - ارتباط بین بخش‌ها با جستجوی متنی انجام می‌شود (مثلاً تطبیق مشتری با موبایل یا نام)، نه با کلید خارجی.
   - به همین دلیل «ارتباط بخش‌ها با هم برقرار نیست».

۳. **حسابداری به فروش وصل نیست؛ فقط کنار آن نشسته است.**
   - فاکتور فروش وقتی به حسابداری می‌رود که صفحهٔ حسابدار یا مدیر باز شود (`aSyncInvoices`).
   - طرف‌حساب از روی نام یا موبایل ساخته می‌شود و ممکن است تکراری شود.
   - اسناد قابل ویرایش‌اند و ردپای قابل اتکا ندارند.

۴. **ادغام سه‌طرفه برای کار هم‌زمان شکننده است.** دو نفر می‌توانند شمارهٔ یکسان بگیرند و ترتیب ثبت تضمین ندارد.

۵. **نقش‌ها ثابت و کدنویسی‌شده‌اند.** `ROLES`، `ROLEPAGES` و `ROLEPERM` در کد ثابت شده‌اند و مدیر نمی‌تواند نقش تازه تعریف کند.

۶. **چاپ از DOM مرورگر است.** صفحهٔ سفید اول، شکستن ناخواسته و تفاوت بین مرورگرها پیش می‌آید.

۷. **محدودیت‌های Google Apps Script:** سهمیهٔ زمان اجرا، اندازهٔ سلول، نبود تراکنش و نبود جستجوی واقعی.

> **قاعده برای تیم:** از کد پروتوتایپ فقط *رفتار* و *ظاهر* را بگیرید، نه ساختار داده یا کد آن را.

## ۲. معماری هدف

### ۲.۱ نمای کلی

```
                ┌────────────────────────────── Next.js (فرانت) ──────────────────────────────┐
                │ سایت عمومی (کاتالوگ، جستجو، سبد استعلام)  │  پنل کارکنان (ماژول‌ها بر اساس مجوز) │
                └───────────────────────────────┬──────────────────────────────────────────────┘
                                                │ REST/JSON (OpenAPI) + JWT/Session
┌───────────────────────────────────────────────┴──────────────────────────────────────────────┐
│                                Django — مونولیت ماژولار                                       │
│  core/iam  │ catalog │ search │ crm │ sales │ inventory │ accounting │ treasury │ payroll │    │
│  documents(print) │ secretariat │ catalog_builder │ settings │ audit │ notifications          │
│                                                                                              │
│  ارتباط بین ماژول‌ها: (۱) سرویس عمومی هر ماژول (services.py)  (۲) رویداد دامنه از جدول outbox     │
└──────┬──────────────────────┬─────────────────────────┬──────────────────────────────────────┘
       │                      │                         │
  PostgreSQL 16          Elasticsearch 8           Redis + Celery
 (منبع حقیقت)         (فقط ایندکس جستجو)       (صف رویداد، PDF، ایمیل/پیامک)
```

### ۲.۲ قواعد ماژولار بودن

- هر ماژول یک Django app است. مدل‌ها، `services.py` (API داخلی)، `api/` (REST)، `events.py`، مجوزها و تست‌های خودش را دارد.
- **هیچ ماژولی مستقیم جدول ماژول دیگر را نمی‌نویسد.** خواندن از سرویس عمومی انجام می‌شود و نوشتن از راه فراخوانی سرویس یا رویداد.
- کلید خارجی بین ماژول‌ها مجاز است؛ مثلاً `sales.Invoice.customer → crm.Party`.
- **رویدادهای دامنه** با الگوی Transactional Outbox منتشر می‌شوند: در همان تراکنش در جدول `outbox` نوشته می‌شوند و Celery آن‌ها را پخش می‌کند. نمونه‌ها:
  - `QuoteApproved`
  - `SupplyOrderCompleted`
  - `InvoiceIssued` / `InvoiceVoided` / `ReturnIssued`
  - `PaymentReceived`
  - `ProductCreated` / `ProductUpdated` (برای ایندکس جستجو)
- هر ماژول با **Feature Flag** در تنظیمات روشن یا خاموش می‌شود. ماژول خاموش در منو، API و مجوزها دیده نمی‌شود.
- ماژول‌ها لایه‌بندی دارند تا وابستگی حلقوی پیش نیاید: `core → catalog → crm → inventory → sales → accounting`. حسابداری به فروش وابسته نیست؛ به رویدادهای آن گوش می‌دهد.

### ۲.۳ چندشرکتی (دو فروشنده)

- دو **واحد تجاری** (`BusinessUnit`) وجود دارد: «کارما» و «آلیاژ پیچ کار ماد».
- هر سند فروش، انبار و حسابداری به یک واحد تجاری تعلق دارد. هر واحد دفاتر، سال مالی، شماره‌گذاری، مهر، سربرگ و نشانی خودش را دارد:
  - کارما: نشانی شعبه؛
  - آلیاژ پیچ کار ماد: نشانی دفتر.
- در هیچ رابطی واژهٔ «رسمی/غیررسمی» نمی‌آید؛ همه‌جا نام واحد تجاری نمایش داده می‌شود.
- دسترسی هر کاربر می‌تواند به یک یا هر دو واحد محدود شود (بخش ۳).

## ۳. ماژول دسترسی (IAM) — اولویت اول

### ۳.۱ نیاز مالک

> «خودم بتونم مشخص کنم چه کاربری به چه بخش‌هایی دسترسی داشته باشه.»

### ۳.۲ مدل

```
User ──< UserRole >── Role ──< RolePermission >── Permission
  │                                                  (module.resource.action)
  └──< UserPermissionOverride  (allow/deny برای یک کاربر خاص)
  └──< UserScope               (واحد تجاری، انبار، «فقط رکوردهای خودم»)
```

- **مجوز** = `module.resource.action`. نمونه‌ها:
  - `sales.invoice.view`، `sales.invoice.create`، `sales.invoice.issue`، `sales.invoice.void`، `sales.invoice.print`، `sales.invoice.backdate`
  - `accounting.voucher.post`، `accounting.period.close`
  - `catalog.price.view_cost`
- فهرست مجوزها را **کد** تعریف می‌کند؛ هر ماژول در `permissions.py` ثبت می‌کند. **ترکیب** مجوزها در نقش‌ها را مدیر از پنل می‌سازد.
- **نقش‌های پیش‌فرض** (قابل ویرایش و حذف، به‌جز «مدیر سیستم»): مدیر سیستم، مدیر فروش، کارشناس فروش، کارشناس محصول، حسابدار، کارشناس تأمین/انبار، فقط‌مشاهده، مشتری.
- **محدوده (Scope):**
  - واحد تجاری؛
  - انبار؛
  - `own_only` (فقط اسنادی که خودش ساخته یا مسئولش است).
- **سطح فیلد:** دیدن قیمت تمام‌شده، سود و ماندهٔ حساب مشتری مجوز جدا دارد. API این فیلدها را برای کاربر بی‌مجوز اصلاً برنمی‌گرداند.
- **اعمال در بک‌اند:** هر endpoint یک permission class دارد. منوی فرانت از `GET /api/me/permissions` ساخته می‌شود.

### ۳.۳ رابط مدیریت

- **ماتریس نقش × مجوز:** ردیف‌ها ماژول‌ها و منابع‌اند (قابل جمع‌شدن) و ستون‌ها عملیات (مشاهده، ایجاد، ویرایش، حذف، تأیید، چاپ، خروجی).
- **صفحهٔ کاربر:**
  - نقش‌ها؛
  - استثناها (allow/deny)؛
  - محدوده‌ها؛
  - «پیش‌نمایش منوی این کاربر».
- **امنیت حساب:**
  - غیرفعال‌سازی؛
  - تعیین رمز؛
  - اجبار 2FA برای مدیر و حسابدار؛
  - خروج از همهٔ نشست‌ها.
- **گزارش ممیزی (audit):** هر تغییر نقش یا مجوز و هر ورود ناموفق ثبت می‌شود.

### ۳.۴ معیار پذیرش

- [ ] مدیر نقش تازهٔ «کارشناس فروش کارما» می‌سازد که فقط پیش‌فاکتور و فاکتورِ واحد کارما را می‌بیند. با این نقش، صدا زدن مستقیم API فاکتورِ آلیاژ پیچ کار ماد **۴۰۳** برمی‌گرداند.

## ۴. کاتالوگ و کد کالا

### ۴.۱ مدل داده

```
Standard (DIN933, ISO4017, ASTM A325 …)
   ├── StandardEquivalent (DIN933 ≈ ISO4017 ≈ «پیچ شش‌گوش تمام‌رزوه»)
   ├── DimensionTable (سطرهای جدول ابعاد؛ از DIN_full_tables.json)
   └── Product (یک ترکیب فروش‌پذیر)
          attrs: size (M10), pitch, length (30), grade/class (8.8), finish (ZN), material, head, drive …
          system_code   = KR-100014                      ← پایدار، هرگز تغییر نمی‌کند
          technical_code= DIN933-M10X30-8.8-ZN          ← از روی ویژگی‌ها ساخته می‌شود
          ProductAlias  (کد قدیمی، کد تأمین‌کننده، نام بازاری، کد ISO معادل)
```

### ۴.۲ کد فنی و کد سیستمی

| کد | کاربرد | قاعده |
|---|---|---|
| `id` (bigint/UUID) | کلید داخلی دیتابیس | هرگز نمایش داده نمی‌شود |
| **کد سیستمی** `KR-100014` | کلید تجاری پایدار؛ در انبار، حسابداری، فاکتور و API | یک بار صادر می‌شود و **هرگز** تغییر نمی‌کند یا دوباره استفاده نمی‌شود. کدهای KR فعلی حفظ می‌شوند. |
| **کد فنی** `DIN933-M10X30-8.8-ZN` | چیزی که کاربر در فرانت می‌بیند و جستجو می‌کند | قطعی و یکتا، ساخته‌شده از ویژگی‌ها: `{standard}-{size}[X{length}]-{grade}-{finish}` (همان `techCode` فعلی) |

- **جدول نگاشت** (`ProductCodeMap` / `ProductAlias`):
  - هر کد فنی دقیقاً به یک کد سیستمی می‌رسد.
  - اگر ویژگی‌ها اصلاح شود، کد فنی تازه ساخته می‌شود و کد فنی قبلی به‌صورت alias باقی می‌ماند تا لینک‌ها، جستجو و سفارش‌های قدیمی کار کنند.
  - کد معادل ISO و کد تأمین‌کننده‌ها هم alias هستند.
- قید یکتایی روی ترکیب ویژگی‌ها در دیتابیس باشد تا دو کد سیستمی برای یک کالا ساخته نشود.
- APIها:
  - `GET /api/products/resolve?code=…`: هر نوع کد (فنی، سیستمی یا alias) را می‌گیرد و کالای واحد را برمی‌گرداند.
  - صدور کد تازه از فرم «تعریف کالا»، تکی یا گروهی (چند سایز × چند طول × چند گرید). رفتار فعلی پروتوتایپ را ببینید.

### ۴.۳ مهاجرت داده

- [ ] همهٔ `KR-` فعلی با همان شماره منتقل شوند. اسکریپت مهاجرت تعداد کدها را قبل و بعد مقایسه کند.

## ۵. جستجوی هوشمند — Elasticsearch

### ۵.۱ هدف

کاربر هر طور که در بازار می‌گوید تایپ کند و سیستم بفهمد. نمونه‌ها:

| ورودی کاربر | برداشت درست |
|---|---|
| `پیچ آلن ۸ در ۲۰ ۱۲.۹` | DIN912 / ISO4762، M8، طول 20، گرید 12.9 |
| `m10x30 8.8 گالوانیزه` | M10، طول 30، گرید 8.8، پوشش ZN |
| `شش گوش ۱۲*۵۰` | DIN933/931، M12، طول 50 |
| `مهره ۱۶` | DIN934 / ISO4032، M16 |
| `واشر فنری ۱۰` | DIN127، M10 |
| `din 933 m 10` | DIN933، M10 |
| `KR-100014` یا `DIN933-M10X30-8.8-ZN` | تطبیق دقیق کد |
| `A325 3/4` | ASTM A325، 3/4" |

### ۵.۲ معماری

- **PostgreSQL منبع حقیقت است**؛ Elasticsearch فقط ایندکس است. همگام‌سازی با رویدادهای `ProductCreated` و `ProductUpdated` از outbox انجام می‌شود، به‌علاوهٔ فرمان `reindex` کامل با alias swap و بدون قطعی.
- **ایندکس‌ها:** `products`، `standards`. برای پنل: `customers`، `documents`.
- **خط لولهٔ پرس‌وجو:**
  1. **نرمال‌سازی:**
     - ي→ی و ك→ک؛
     - ارقام فارسی و عربی به لاتین؛
     - حذف نیم‌فاصله و اعراب؛
     - `×` `*` `x` «در» → `X`؛
     - `m 10` → `M10`؛
     - کسر اینچی `3/4`.
  2. **پارسر پارامتر (Query Understanding):** با قاعده و دیکشنری، توکن‌ها را به فیلدهای ساخت‌یافته تبدیل می‌کند:
     - `type`، `standard`، `size`، `length`، `grade`، `finish`، `material`؛
     - خروجی: فیلترهای ساخت‌یافته + متن باقی‌مانده.
     - این لایه در بک‌اند (Python) است تا قابل تست واحد باشد.
  3. **کوئری Elasticsearch:**
     - `bool`: فیلترهای ساخت‌یافته (با boost، نه حذف سخت)؛
     - `multi_match` روی نام فارسی، نام بازاری، کد و aliasها؛
     - `fuzziness: AUTO` برای غلط تایپی.
  4. **رتبه‌بندی:**
     - تطبیق دقیق کد؛
     - سپس تطبیق کامل پارامترها؛
     - سپس اولویت فروش استاندارد (همان «priority groups» فعلی)؛
     - سپس موجودی.
  5. **جایگزین نزدیک:** اگر ترکیب دقیق وجود ندارد، نزدیک‌ترین طول یا گرید موجود پیشنهاد شود («M8×22 نداریم؛ M8×20 و M8×25 موجود است»).
- **پیشنهاد حین تایپ (autocomplete):**
  - `completion` suggester و `edge_ngram`؛
  - نتیجه‌ها گروه‌بندی‌شده: استاندارد، کالا، دسته؛
  - پاسخ کمتر از ۱۰۰ms.
- **«منظورتان این بود؟»** با `phrase suggester`.
- **Facets** (aggregations): استاندارد، سایز، طول، گرید، پوشش، جنس. همان فیلترهای کاتالوگ فعلی، ولی از ES.

### ۵.۳ تحلیل‌گر و دیکشنری

- `analyzer` سفارشی: `char_filter` نرمال‌سازی فارسی + `persian_normalization` + `lowercase` + `synonym_graph`.
- **دیکشنری مترادف قابل ویرایش در پنل** (بدون deploy؛ با `reload_search_analyzers`). نمونه‌ها:
  - `آلن, آلنی, سرسیلندر آلن, socket head, DIN912, ISO4762`
  - `شش‌گوش, شش گوش, هگزا, hex bolt, DIN933, DIN931, ISO4017, ISO4014`
  - `گالوانیزه, زینک, ZN, سفید` و `گالوانیزه گرم, HDG`
  - `فنری, واشر فنری, DIN127`
  - `استیل, ضدزنگ, A2, A4`
- **گزارش جستجو:**
  - جستجوهای بی‌نتیجه و پرتکرار ثبت و در داشبورد نمایش داده شوند تا مترادف‌ها کامل شوند؛
  - نرخ کلیک روی نتیجهٔ اول هم اندازه‌گیری شود.

### ۵.۴ معیار پذیرش

## ۶. فروش، مشتریان و اسناد

این بخش همهٔ رفتارهای نسخهٔ 1.3.0 را که مالک تأیید کرده نگه می‌دارد و روی مدل رابطه‌ای درست بازسازی می‌کند.

### ۶.۱ زنجیرهٔ فروش

```
درخواست سایت ─► پیش‌فاکتور (PRF) ─► تأیید مشتری ─► برگهٔ تأمین (SUP) ─► فاکتور (INV) ─► لیست بسته‌بندی (PKL)
                     │ اصلاحیه (‎-1، ‎-2)                                    │ ابطال / برگشتی (RET)
```

- مدل‌ها:
  - `Request`؛
  - `Quote` و `QuoteRevision`؛
  - `SupplyOrder` و `SupplyLine` (مسئول تأمین، مقدار تأمین‌شده، منبع، یادداشت)؛
  - `Invoice` و `InvoiceLine`؛
  - `ReturnInvoice`؛
  - `PackingList` با فیلدهای بسته‌بندی قابل تعریف.
- همهٔ اسناد یک معامله یک **شمارهٔ معامله** (`deal_number`) مشترک دارند و فقط پیشوند سه‌حرفی فرق می‌کند: `PRF-14050801-0232`، `SUP-…`، `INV-…`، `PKL-…`، `RET-…`.
- **شماره‌گذاری در سرور** با قفل یا sequence دیتابیس ساخته می‌شود و یکتایی آن قید دیتابیس است.
  - فاکتور مستقل (بدون پیش‌فاکتور) هنگام صدور شمارهٔ تازه می‌گیرد.
  - پیشوندها و قالب در تنظیمات قابل تغییرند.
- **وضعیت‌ها با ماشین حالت** مدیریت می‌شوند (`draft → sent → approved → invoiced`، `revised`، `void`). هر انتقال مجوز و رویداد خودش را دارد.
- سند صادرشده **قابل ویرایش نیست**؛ فقط ابطال یا برگشتی ممکن است.

### ۶.۲ تاریخ سند قابل انتخاب (نیاز تازه)

- هر سند دو تاریخ جدا دارد:
  - `doc_date`: تاریخ سند. کاربر از تقویم شمسی انتخاب می‌کند و پیش‌فرض آن امروز است.
  - `created_at` / `issued_at`: زمان سیستمی. خودکار پر می‌شود، تغییرناپذیر است و در تاریخچه و ممیزی نمایش داده می‌شود.
- قواعد:
  - تاریخ باید داخل **سال مالی و دورهٔ باز** واحد تجاری باشد؛ دورهٔ بسته‌شده در حسابداری قبول نمی‌شود.
  - تاریخ گذشته‌تر از N روز (قابل تنظیم) یا تاریخ آینده مجوز `sales.invoice.backdate` می‌خواهد.
  - تاریخ سند در شمارهٔ معامله، سند حسابداری، کاردکس انبار و گزارش‌ها همان `doc_date` است.
  - تغییر تاریخ تا قبل از صدور آزاد است؛ بعد از صدور فقط با ابطال.
- معیار پذیرش:
  - [ ] فاکتوری با تاریخ ۱۰ روز قبل صادر شود.
  - [ ] سند حسابداری‌اش همان تاریخ را دارد.
  - [ ] تاریخچه هر دو زمان را نشان می‌دهد.
  - [ ] کاربر بدون مجوز نمی‌تواند تاریخ گذشته بزند.

### ۶.۳ انتخاب مشتری در پیش‌فاکتور و فاکتور (نیاز تازه)

- **انتخابگر مشتری** (combobox) در کادر خریدار:
  - جستجو با نام، موبایل، کد ملی/شناسهٔ ملی، کد اقتصادی و کد مشتری از ES؛
  - هر نتیجه نام، شهر، موبایل و ماندهٔ حساب را نشان می‌دهد (مانده فقط با مجوز)؛
  - «+ مشتری جدید» در همان کادر، بدون ترک صفحه.
- **با انتخاب مشتری:**
  - همهٔ فیلدهای خریدار پر می‌شوند؛
  - شرایط پرداخت پیش‌فرض او و سقف اعتبار اعمال یا هشدار داده می‌شود.
- **عکس فوری (snapshot):** سند، مشخصات خریدار را در لحظهٔ صدور در خودش ذخیره می‌کند تا تغییر بعدی پروفایل سند قدیمی را عوض نکند. کلید `customer_id` هم نگه داشته می‌شود.
- **ویرایش در سند:** کاربر فیلدها را برای همین سند تغییر می‌دهد و با «ذخیره در پرونده» تغییر را به پروفایل برمی‌گرداند.
- **جلوگیری از تکرار:** موبایل و کد ملی یکتا هستند. اگر کاربر مشتری تکراری بسازد، پیشنهاد ادغام داده می‌شود.

### ۶.۴ CRM — پروندهٔ مشتری

- **یک موجودیت `Party`** برای همهٔ ماژول‌ها: فروش، حسابداری (طرف‌حساب) و دبیرخانه. نقش‌های یک Party: مشتری، تأمین‌کننده، کارمند.
  - این همان ایراد «ارتباط بخش‌ها» در نسخهٔ فعلی است که حسابداری طرف‌حساب جدا می‌سازد.
- **فیلدهای پایه:**
  - نام / شرکت؛
  - نوع (حقیقی/حقوقی)؛
  - موبایل؛
  - کد یا شناسهٔ ملی؛
  - کد اقتصادی؛
  - شمارهٔ ثبت؛
  - کد پستی؛
  - نشانی.
- **فیلدهای تکمیلی:**
  - رابط و سمت؛
  - ایمیل؛
  - استان و شهر؛
  - حوزهٔ فعالیت؛

## ۷. حسابداری — بازنویسی کامل با الگوبرداری کارکردی از حسابیکس

### ۷.۱ تصمیم مالک و قواعد کار

**تصمیم (تأییدشده توسط مالک):** از **همهٔ بخش‌های حسابیکس** الگوبرداری کارکردی می‌شود. مالک صریحاً روی دو چیز تأکید دارد:
- **منطق حسابداری** حسابیکس؛
- **بخش‌هایی که حسابیکس دارد.**

هر دو در سامانهٔ کارما از نو نوشته می‌شوند.

**دربارهٔ منبع:**
- مخزن `github.com/morrning/hesabixCore`؛ PHP/Symfony و رابط Vue.
- آخرین commit بررسی‌شده: `8adfdb0` در ۱۱ ژوئیهٔ ۲۰۲۵. در همین تاریخ آرشیو شده و ادامهٔ توسعه در `source.hesabix.ir` است.
- مجوز هسته **AGPL-3.0** و رابط کاربری GPL-3.0 است.

**قواعد clean-room (الزامی):**
1. مرجع پیاده‌سازی **فقط همین فصل** است. این فصل رفتار حسابیکس را به زبان کارکردی توصیف می‌کند، نه کد آن را.
2. توسعه‌دهندگان کارما **کد حسابیکس را باز نمی‌کنند**. هیچ فایل، تابع، کوئری، قالب چاپ یا ساختار جدولی از آن کپی یا ترجمه نمی‌شود.
3. نام‌گذاری، ساختار داده و کد کارما مستقل است (Django/Python، طراحی بخش ۲).
4. اگر جزئیاتی لازم شد که این فصل ندارد، از **اجرای نسخهٔ نصب‌شدهٔ حسابیکس** یا مستندات کاربری آن گرفته شود. سؤال به نویسندهٔ مشخصات برگردد، نه به کد.
5. پیش از انتشار، یک بازبینی تشابه کد انجام و ثبت شود. مسئول آن بازبین ارشد تیم است.

> **نکتهٔ مهم:** هر جا حسابیکس از نظر حسابداری خطا دارد، **منطق اصلاح‌شده** در این فصل آمده و ملاک همان است (بخش‌های ۷.۴ و ۷.۹).

### ۷.۲ اصول طراحی

- **دفترکل دوطرفه با تراز اجباری:** هر سند Σ بدهکار = Σ بستانکار دارد. این قید در سرویس و در دیتابیس (constraint یا trigger) اعمال می‌شود.
- **تغییرناپذیری:**
  - سند «دائم» هرگز ویرایش یا حذف نمی‌شود؛ اصلاح فقط با **سند معکوس**.
  - سند «موقت» قابل ویرایش است.
  - سند «پیش‌نویس» در تراز نمی‌آید.
- **حسابداری به رویداد گوش می‌دهد:** فروش، انبار، خزانه و حقوق مستقیم سند نمی‌زنند. رویداد منتشر می‌کنند و **موتور قواعد ثبت** (Posting Rules، بخش ۷.۴) سند را می‌سازد.
- نگاشت رویداد به حساب‌ها **در تنظیمات قابل ویرایش** است و پیش‌فرض آن جدول ۷.۴ است. هیچ کد حسابی در کد برنامه ثابت نمی‌شود.
- **ثبت هم‌زمان:** سند در همان تراکنش یا با outbox تضمین‌شده (at-least-once + idempotency key) ثبت می‌شود. «باید حسابدار صفحه را باز کند» دیگر وجود ندارد.
- **ردگیری دوطرفه:** از هر عملیات به سند حسابداری‌اش و از هر سند به عملیات مبدأ لینک هست.

### ۷.۳ منطق محوری حسابیکس که عیناً الگو گرفته می‌شود

#### الف) یک دفتر روزنامه؛ همهٔ دفترهای فرعی از ردیف‌های آن

حسابیکس دفتر جداگانه برای بانک، صندوق، شخص یا چک نگه نمی‌دارد. **همه‌چیز سند حسابداری است** و هر ردیف سند، علاوه بر حساب کل/معین، به یک «موجودیت تفصیلی» اشاره می‌کند:
- شخص؛
- حساب بانکی؛
- صندوق؛
- تنخواه‌گردان؛
- چک؛
- کالا، همراه با **تعداد**.

گردش و ماندهٔ هر بانک، شخص، صندوق یا کالا (کارت حساب) فقط **فیلتر همین ردیف‌ها** است.

**در کارما:**
- مدل `VoucherLine` این ستون‌ها را دارد:
  - `account` (حساب معین)
  - `party`
  - `bank_account`
  - `cash_box`
  - `petty_cash`
  - `cheque`
  - `product` و `quantity`
  - `project`
  - `cost_center`
  - `business_unit`
  - `debit` و `credit`
  - `description`
- مانده‌ها از ردیف‌ها محاسبه می‌شوند. برای سرعت، materialized view یا جدول تجمیعی داریم که با رویداد به‌روز می‌شود، ولی منبع حقیقت ردیف‌هاست.

#### ب) نوع هر حساب تعیین می‌کند چه تفصیلی‌ای بپذیرد

- در جدول حساب‌های حسابیکس هر گره یک «نوع» دارد:
  - محاسباتی (فقط کل/معین)؛
  - شخص؛
  - بانک؛
  - صندوق؛
  - تنخواه؛
  - چک.
- فقط ردیفی که تفصیلی متناسب دارد روی آن حساب می‌نشیند. مثلاً «حساب‌های دریافتنی» از نوع شخص است.

**در کارما:** هر `Account` فیلد `detail_kinds` (یک یا چند نوع) و `detail_required` دارد. اعتبارسنجی سرویس ردیفی را که تفصیلی لازم را ندارد رد می‌کند.

#### ج) هر عملیات = یک نوع سند

حسابیکس برای هر عملیات تجاری یک «نوع سند» دارد و همه در همان جدول اسناد می‌نشینند:

| نوع سند | معنی |
|---|---|
| `sell` | فاکتور فروش |
| `buy` | فاکتور خرید |
| `rfsell` | برگشت از فروش |
| `rfbuy` | برگشت از خرید |
| `person_receive` | دریافت از شخص |
| `person_send` | پرداخت به شخص |
| `sell_receive` | دریافت وجه فاکتور فروش |
| `buy_send` | پرداخت وجه فاکتور خرید |
| `transfer` | انتقال بین بانک، صندوق و تنخواه |
| `cost` | سند هزینه |
| `income` | سند درآمد |
| `open_balance` | تراز افتتاحیه |
| `pass_cheque` | وصول چک |
| `reject_cheque` | برگشت چک |
| `transfer_cheque` | واگذاری (خرج) چک |
| `modify_cheque` / `modify_cheque_output` | ثبت یا ویرایش چک دریافتی/پرداختی |
| `calc` | سند دستی |
| `walletPay` | پرداخت آنلاین |
| (افزونه‌ها) | سند حقوق، اقساط و … |

**در کارما:** همین فهرست به‌صورت `Voucher.source_type` و لینک به موجودیت مبدأ نگه داشته می‌شود. فاکتور، رسید و چک موجودیت‌های ماژول خودشان‌اند و سند حسابداری‌شان جدا ولی **یک‌به‌یک لینک‌شده** است.
- در حسابیکس خود فاکتور همان سند حسابداری است.
- در کارما جدا می‌شود تا قانون «سند دائم تغییرناپذیر» با گردش فروش تداخل نکند.

#### د) اسناد مرتبط و وضعیت پرداخت فاکتور

- در حسابیکس، دریافت وجه فاکتور سندی جداست که به فاکتور «مرتبط» می‌شود (`relatedDocs`). جمع دریافت‌های مرتبط، مانده و وضعیت پرداخت فاکتور را می‌سازد.
- فاکتور برچسب هم دارد: «تسویه شده»، «مرجوع شده»، «تأیید شده».
- هنگام صدور فاکتور می‌شود همان‌جا یک یا چند دریافت (بانک، صندوق، تنخواه) ثبت کرد. هر کدام سند جدای مرتبط می‌سازد.

**در کارما:**
- `Payment` ↔ `Invoice` چندبه‌چند با مبلغ تخصیص‌یافته (allocation)، تا یک دریافت چند فاکتور را تسویه کند.
- وضعیت پرداخت فاکتور (پرداخت‌نشده، بخشی، تسویه) محاسبه‌شده است، نه دستی.
- سررسید و «فاکتورهای معوق» هم از همین محاسبه می‌آید.

#### هـ) قواعد ویرایش و حذف

- **حسابیکس:**
  - فاکتور فقط وقتی ویرایش می‌شود که در **سال مالی جاری** باشد و **هیچ حوالهٔ انباری** برایش صادر نشده باشد.
  - حذف سند اسناد مرتبط را هم پاک می‌کند (به‌جز پرداخت آنلاین) و اگر حوالهٔ انبار وجود داشته باشد پیغام می‌دهد.
- **کارما:**
  - این قواعد حفظ می‌شود: ویرایش فقط در دورهٔ باز و پیش از خروج انبار.
  - «حذف» تبدیل به **ابطال با سند معکوس** می‌شود.
  - ابطال فاکتوری که دریافت یا برگشتی فعال دارد ممنوع است، مگر اول آن‌ها باطل شوند (رفتار تأییدشدهٔ نسخهٔ فعلی کارما).

#### و) سال مالی و ارز

- **حسابیکس:**
  - هر کسب‌وکار چند سال مالی دارد و یکی «جاری» است. همهٔ اسناد و ردیف‌ها به سال تعلق دارند.
  - هر کسب‌وکار یک ارز اصلی و ارزهای اضافه دارد. **اسناد هر ارز دفتر جدا دارند.**
- **کارما:**
  - سال مالی و دوره‌های ماهانه برای هر واحد تجاری.
  - ارز پایه ریال است.
  - ردیف می‌تواند `currency` و `fx_rate` و `amount_fx` داشته باشد. مبلغ ریالی همیشه پر است و تراز با ریال سنجیده می‌شود.
  - تسعیر ارز پایان دوره سند خودکار با حساب «سود/زیان تسعیر» می‌زند.

#### ز) شماره‌گذاری

- **حسابیکس:** شمارنده‌های جدا برای سند حسابداری، شخص، کالا، بانک، صندوق، تنخواه، انبار و … در سطح کسب‌وکار.
- **کارما:**
  - شمارنده‌ها با sequence دیتابیس و قید یکتایی.
  - شمارهٔ سند حسابداری به ازای سال مالی و واحد تجاری، **بی‌فاصله** (gapless).
  - شمارهٔ معاملهٔ فروش طبق بخش ۶.۱.

### ۷.۵ چرخهٔ چک

حسابیکس برای چک یک موجودیت جدا دارد که به ردیف سند وصل است. مشخصات چک:
- شماره؛
- **شمارهٔ صیادی**؛
- بانک؛
- تاریخ سررسید؛
- صاحب چک (شخص)؛
- نوع (دریافتی یا پرداختی)؛
- وضعیت: وصول‌نشده، وصول، برگشت‌خورده، واگذارشده.

هر تغییر وضعیت یک سند خودکار می‌زند و چک قفل یا آزاد می‌شود. کارما همین ماشین حالت را می‌سازد، با حساب‌های اصلاح‌شده:

**چک دریافتی**

```
ثبت ──► نزد صندوق ──(واگذاری به بانک)──► در جریان وصول ──► وصول‌شده
            │                                   │
            ├──(خرج/واگذاری به شخص)──► خرج‌شده   └──► برگشت‌خورده ──(تعویض/وصول نقدی)──► تسویه
```

| انتقال | سند |
|---|---|
| ثبت | بد `1202 اسناد دریافتنی` [چک] · بس `1201 دریافتنی` [مشتری] |
| واگذاری به بانک | بد `1203 چک‌های در جریان وصول` · بس `1202` |
| وصول | بد `1102 بانک` · بس `1203` (یا `1202` اگر واگذاری ثبت نشده) |
| برگشت | بد `1204 چک‌های برگشتی` [مشتری، چک] · بس `1203` یا `1202`؛ مانده به بدهی مشتری برمی‌گردد |
| خرج به تأمین‌کننده | بد `3101 پرداختنی` [تأمین‌کننده] · بس `1202` |
| لغو برگشت (حسابیکس دارد) | سند معکوس آخرین «برگشت» |

**چک پرداختی**

| انتقال | سند |
|---|---|
| صدور | بد `3101` [تأمین‌کننده] · بس `3102 اسناد پرداختنی` [چک] |
| پاس | بد `3102` · بس `1102 بانک` |
| برگشت | بد `3102` · بس `3101` [تأمین‌کننده] |

قواعد:
- چک قفل‌شده (وصول یا خرج‌شده) ویرایش نمی‌شود.
- **یادآوری سررسید** n روز قبل (اعلان و پیامک).
- فهرست «چک‌های قابل خرج» در فرم پرداخت.

### ۷.۶ انبار و بهای تمام‌شده

**الگوی حسابیکس:**
- انبار سند مقداری دارد: **حواله** (رسید یا خروج).
- حواله همیشه **به یک فاکتور ارجاع دارد** (فروش، خرید، برگشت از فروش یا برگشت از خرید)، یا از نوع ضایعات یا مصرف مستقیم است.
- تحویل **بخشی** مجاز است، ولی بیشتر از مقدار فاکتور نه.
- روش ارسال (درب انبار، پست، باربری، تیپاکس، پیک) و انباردار ثبت می‌شود.
- موجودی هر کالا = Σ ورود − Σ خروج.
- سود فاکتور با یکی از سه روش تنظیمی **فقط در گزارش** محاسبه می‌شود: آخرین قیمت ورود، میانگین قیمت ورود، یا اختلاف خرید و فروش.
- بهای تمام‌شده سند حسابداری نمی‌زند.

**کارما:**
- همان الگوی حواله‌به‌ارجاع‌فاکتور.
  - برگهٔ تأمین (SUP) و لیست بسته‌بندی (PKL) کارما همان «حوالهٔ خروج برای فاکتور فروش» هستند و تحویل بخشی را پشتیبانی می‌کنند.
- **موجودی دائمی با میانگین موزون متحرک**: هر حوالهٔ خروج همان لحظه سند بهای تمام‌شده می‌زند (۷.۴).
- تنظیم «خروج خودکار هنگام صدور فاکتور» برای فروش‌هایی که برگهٔ تأمین ندارند.
- **ضایعات و کسری:** بد `7601 کسری و ضایعات` · بس `1301`. **اضافهٔ انبار:** بد `1301` · بس `6202 اضافهٔ کالا`.
- **انتقال بین انبارها** سند مالی ندارد (فقط مقداری)؛ تفصیلی انبار عوض می‌شود.
- **نقطهٔ سفارش و حداقل سفارش** (از حسابیکس) و هشدار کمبود.
- **واحد با دقت اعشار:** عدد ۰ رقم، کیلوگرم ۳ رقم. این برای پیچ و مهره حیاتی است چون هم عددی و هم کیلویی فروخته می‌شود.
  - هر کالا **ضریب تبدیل** «وزن هر ۱۰۰۰ عدد» دارد و از جدول‌های DIN پر می‌شود.
  - تبدیل عدد ↔ کیلو در فاکتور و انبار خودکار است. کاردکس با واحد پایه نگه داشته می‌شود.
- **کاردکس کالا:**
  - هر ورود و خروج، با مقدار، بهای واحد، بهای کل و ماندهٔ مقداری و ریالی پس از هر رویداد؛
  - گزارش «خرید و فروش به تفکیک کالا».

### ۷.۷ سال مالی، افتتاحیه، اختتامیه

**حسابیکس:**
- بستن سال در یک صفحه انجام می‌شود. ابتدا ترازنامه و مانده‌ها نمایش داده می‌شود: دارایی‌ها، بانک‌ها، صندوق‌ها، تنخواه‌ها، بدهکاران و بستانکاران.
- توصیه می‌شود اصلاحات پیش از بستن ثبت شود.
- تراز افتتاحیه برای بانک، صندوق، تنخواه، اشخاص، کالا (تعداد × قیمت) و سهامداران از یک صفحه وارد می‌شود.

**کارما:**
1. **پیش‌بررسی:**
   - تراز آزمایشی؛
   - اسناد پیش‌نویس یا موقت باقی‌مانده؛
   - چک‌های بی‌وضعیت؛
   - حواله‌های بی‌فاکتور؛
   - مغایرت موجودی مقداری با ریالی.
2. **بستن حساب‌های موقت:** درآمدها و هزینه‌ها ← `8201 خلاصهٔ سود و زیان` ← `5301 سود (زیان) انباشته`.
3. **سند اختتامیه:** همهٔ حساب‌های دائمی ← `8401 تراز اختتامیه`.
4. **سند افتتاحیهٔ** سال بعد به‌صورت خودکار، با حفظ تفصیلی‌ها (شخص، بانک، کالا با مقدار و بهای میانگین، چک‌های باز).
5. سال بسته **فقط‌خواندنی** است.
6. باز کردن دوبارهٔ سال فقط با مجوز `accounting.year.reopen`. اسناد اختتامیه و افتتاحیه حذف و دوباره ساخته می‌شوند.

### ۷.۹ نقاط ضعف حسابیکس که تکرار نمی‌شود

این موارد در نسخهٔ بررسی‌شده دیده شد. تیم کارما **عکس آن** را پیاده می‌کند:

1. **نبود کنترل تراز:** ثبت سند دستی برابری جمع بدهکار و بستانکار را در سرور چک نمی‌کند. ← قید تراز در سرویس و دیتابیس.
2. **ویرایش با پاک‌کردن ردیف‌ها:** ویرایش سند ردیف‌های قبلی را حذف و از نو می‌سازد و سند دائم یا معکوس وجود ندارد. ← وضعیت‌های پیش‌نویس، موقت و دائم + سند معکوس.
3. **کد حساب ثابت در کد برنامه:** هر کنترلر شمارهٔ حساب را مستقیم می‌نویسد. ← موتور قواعد ثبت با نگاشت قابل تنظیم.
4. **حساب‌های نادرست در چند عملیات:**
   - برگشت از فروش به «موجودی کالا» بدهکار می‌شود؛
   - برگشت از خرید به «فروش» بستانکار می‌شود؛
   - مالیات خرید جزء موجودی ثبت می‌شود؛
   - تخفیف فروش به هزینهٔ توزیع می‌رود؛
   - طرف تراز افتتاحیهٔ سهامداران روی حساب بانک می‌نشیند.
   - ← جدول ۷.۴.
5. **موجودی ادواری بدون سند بهای تمام‌شده:** سود فقط در گزارش محاسبه می‌شود. ← موجودی دائمی با میانگین موزون.
6. **چندارزی به‌صورت دفترهای جدا:** تبدیل و تسعیر بین ارزها مشاهده نشد. ← ارز در سطح ردیف با نرخ و سند تسعیر.
7. **دسترسی بولی و درشت‌دانه.** ← RBAC بخش ۳.
8. **مؤدیان پیاده نشده.** ← فاز ۶.
9. **شمارنده بدون قفل صریح.** ← sequence و قید یکتایی، شمارهٔ بی‌فاصله برای اسناد حسابداری.

### ۷.۱۲ مهاجرت از نسخهٔ فعلی

- [ ] طرف‌حساب‌های فعلی (`A.parties`) با `crm.Party` ادغام شوند. کلید ادغام: موبایل، سپس کد ملی، سپس بازبینی دستی تکراری‌ها.
- [ ] حساب‌های نسخهٔ فعلی (`A.coa`) به جدول ۷.۱۰ نگاشت شوند. جدول نگاشت را حسابدار تأیید کند.
- [ ] اسناد فعلی (`A.vouchers`) با همان شماره و تاریخ به‌صورت سند «موقت» وارد شوند. پس از تطبیق تراز با نسخهٔ قدیم، دائم شوند.
- [ ] فاکتورهای فروش فعلی به فاکتور جدید و سند متناظرش لینک شوند.
- [ ] چک‌ها با وضعیت فعلی، و موجودی کالا با مقدار و بهای میانگین به‌عنوان افتتاحیه منتقل شوند.
- [ ] **گزارش تطبیق:** تراز آزمایشی قبل و بعد از مهاجرت عیناً برابر باشد.

### ۷.۱۳ معیار پذیرش

- [ ] صدور فاکتور (بدون باز کردن صفحهٔ حسابداری) ظرف چند ثانیه سند درآمد می‌سازد. تکمیل برگهٔ تأمین سند بهای تمام‌شده می‌سازد. مانده‌ها درست است.
- [ ] برای هر ردیف جدول ۷.۴ یک تست یکپارچه وجود دارد که حساب‌ها، تفصیلی‌ها و مبالغ سند را دقیقاً چک می‌کند.
- [ ] همهٔ انتقال‌های ماشین حالت چک (۷.۵)، از جمله برگشت و لغو برگشت، تست دارند.
- [ ] ثبت سندی که Σ بدهکار ≠ Σ بستانکار باشد، یا ردیفی که تفصیلی لازم را ندارد، رد می‌شود.
- [ ] ابطال فاکتور سند معکوس می‌سازد؛ سند اصلی دست نمی‌خورد.
- [ ] ثبت سند در دورهٔ بسته‌شده رد می‌شود.
- [ ] بستن سال (۷.۷) روی دادهٔ نمونه انجام شود و افتتاحیهٔ سال بعد با اختتامیه برابر باشد.
- [ ] کاردکس کالا با Σ ردیف‌های حساب `1301` آن کالا برابر است (مقداری و ریالی).
- [ ] تست‌های خودکار در هر حالتی تراز را نگه می‌دارند (property-based: هر ترکیبی از عملیات → تراز آزمایشی تراز است).
- [ ] گزارش بازبینی تشابه کد (۷.۱) پیش از انتشار ثبت شده است.

## ۹. فرانت و UI

خواستهٔ مالک: «فرانت و UI جذابیت بیشتری داشته باشد.»

- **سیستم طراحی:**
  - توکن‌های رنگ، فاصله و تایپوگرافی؛
  - فونت **Vazirmatn** (ارقام فارسی در متن؛ ارقام لاتین برای کدها و مبالغ جدول، طبق قاعدهٔ فعلی)؛
  - تم روشن و تیره؛
  - کامپوننت‌های مشترک (جدول داده، فرم، combobox، تقویم شمسی، دیالوگ، toast)؛
  - Storybook برای مستندسازی.
- **RTL واقعی:** CSS logical properties؛ آیکن‌ها و جهت‌ها برعکس؛ جداکنندهٔ اعشار نقطه (قاعدهٔ تأییدشده).
- **پنل کارکنان:**
  - داشبورد هر نقش با شاخص‌های کلیدی؛
  - جستجوی سراسری Ctrl+K؛
  - جدول‌ها با فیلتر، مرتب‌سازی، ذخیرهٔ نما و خروجی؛
  - ورود سریع ردیف فاکتور با کیبورد (Enter، Tab، جستجوی کالا درون ردیف)؛
  - ذخیرهٔ خودکار پیش‌نویس.
- **سایت عمومی:**
  - سبک بنرهای تمام‌صفحه و هدر ثابت تطبیقی (تأییدشده در پروتوتایپ)؛
  - تصاویر بهینه (next/image، WebP)؛
  - SEO برای صفحه‌های استاندارد (SSR، schema.org Product)؛
  - صفحهٔ ورود ساده.
- **واکنش‌گرا:** موبایل برای سایت و برای برگهٔ تأمین (کار در انبار با گوشی).
- **دسترس‌پذیری:** کنتراست AA، فوکوس کیبورد، برچسب فرم‌ها.
- **مرجع ظاهر:** پروتوتایپ فعلی. تیم طراحی می‌تواند بهبود دهد ولی ساختار اطلاعات و گردش کار تأییدشده را عوض نکند.

## ۱۲. پرسش‌های باز برای مالک

1. **جدول حساب پیش‌فرض (۷.۱۰) و قواعد ثبت (۷.۴):** حسابدار شرکت پیش از فاز ۴ تأیید کند. *(مسیر حسابیکس تعیین شده: الگوبرداری کارکردی از همهٔ بخش‌ها.)*
2. آیا دو واحد تجاری دفاتر کاملاً جدا دارند یا گزارش تلفیقی هم لازم است؟
3. حداکثر چند روز تاریخ گذشته برای فاکتور مجاز است و چه نقشی می‌تواند؟
4. اتصال به سامانهٔ مؤدیان برای کدام واحد و از چه زمانی؟
5. محل میزبانی: سرور داخل شرکت یا ابر داخلی؟ دامنهٔ نهایی؟
6. آیا مشتریان سایت باید پرداخت آنلاین داشته باشند (درگاه)؟
7. لیست نهایی نقش‌ها و اینکه هر نقش دقیقاً چه ببیند. نقش‌های پیش‌فرض بخش ۳ نقطهٔ شروع است.
